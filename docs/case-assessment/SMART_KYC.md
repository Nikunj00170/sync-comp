# Smart KYC implementation

The prototype uses only synthetic case registries and the case's fixed validation date, 15 July 2026. It does not perform government identity verification, DigiLocker retrieval, e-signing or real service activation.

Authenticated customers upload private bytes, complete uploads, then explicitly consent to OCR and registry checks. POST `/v1/kyc/assessment` extracts only completed documents owned by that JWT subject. Reports return masked identifiers and review reasons. POST `/v1/registries/lookup` accepts one identifier in a bounded JSON body, requires the same consent and returns a masked synthetic lookup result. Registry data is packaged only on the backend. The complete dataset is never sent to the browser.

Checks include GST structure and checksum (accepting the fictional PAN entity character X), registry presence and Active status, document/registry/profile business names, registration/address consistency, address proof no older than 90 days, signatory expiry and required document kinds. Ambiguous OCR is sent for review, without guessing digits or resolving a number from a business name. Synthetic verification now requires a successful assessment; consent and arbitrary uploads cannot bypass it. Business/address/GST profile changes invalidate prior approval and consent. Concurrent document or consent changes prevent approval through conditional writes.

Default `SYNC_KYC_OCR=fixtures` matches SHA-256 of the actual 47 supplied PNGs to cached **Tesseract output**, not expected decisions or judge data. Unknown bytes produce a review result. Regenerate with `python3 scripts/rebuild-kyc-ocr.py` and installed Tesseract. This mode is a reproducible specimen demo, not general OCR. `SYNC_KYC_OCR=textract` reads the owned object and calls AWS Textract using the execution role; it conservatively supports clear PNG/JPEG up to 5 MiB and discards low-confidence lines. Other files require review. This adapter is tested with SDK mocks; it has not been exercised against a live AWS account.

`KycChecksTest` hashes and processes all 47 actual files grouped into 12 applicants. It asserts a readable active example can pass (K05), cancelled registration is flagged (K01), unreadable documents remain reviewable (K02/K04), and an old bill is flagged (K11). These are independently derived checks against student-visible documents, not a claim of matching hidden judge labels. The browser full-stack journey uses K05 PNGs and reaches a server-created order and invoice on both desktop and mobile.
